# 饮食 Agent 可复现评测

本目录用于产生实测结果。目标值不写入成功计数，不按目标值修改标准答案。

## 数据与标注

- `corpus.json`：600 条意图样本、100 组任务、120 次故障注入的固定定义。
- `corpus-preview.md`：120 个意图语义种子的可读预览。
- 600 条意图样本由 **120 个语义种子各产生 5 个相关表达**，六类各 100 条。不能称为 600 个独立真实用户样本。
- 来源是 **AI 辅助构造与标注，未经过独立人工复核**。`humanReviewed=false` 明示这一点。
- `groupId` 用于按语义种子分组；以后划分开发集/测试集必须按组划分，不能把同一种子的变体拆到两边。
- 意图准确率以最终规则修正后的意图为准。槽位标签只使用 SQL 中存在的标签；语义歧义通过 `rationale` 解释。
- 多轮分为 60 组澄清补槽、30 组推荐调整、10 组多餐规划。每组固定用户输入，不根据系统答错的内容偷偷改写下一轮或答案。
- 否定词、引用风险词、跨领域请求可能暴露当前关键词规则的误判。这些失败仍保留。
- 调试了这些样本后，它们就属于已见回归集；需要另建未见测试集才能报告泛化能力。

标注版本1.1补充了调整轮的“清淡”偏好继承和“快速”槽位检查。版本1.0的运行记录保留；使用`regrade.py`对相同原始响应统一重新评分，不修改用户输入、不重写模型输出。

标注字段：

| 字段 | 含义 |
|---|---|
| `message` | 用户输入 |
| `expectedIntent` | 路由标准答案 |
| `expectedSlots` | 明示槽位标签；意图集的主指标只统计路由，不能把它当完整槽位金标准 |
| `context` | 预设累计槽位、历史餐食 ID 与最近对话 |
| `requiredSlots` | 多轮结束时必须保留或补齐的槽位值 |
| `allowedSlots` | 可接受的完整槽位取值上界；未表达的偏好不能随意添加 |
| `routes` | 当前任务轮次可接受的路由集合；独立意图集仍是单一标准答案 |
| `requiresCards` / `minCards` | 必须实际返回推荐，以及最低数量 |
| `requiredMealTimes` | 多餐规划必须覆盖的餐次 |
| `isAdjust` | 与此前实际展示过的所有 ID 比较重复 |

`CLARIFY_NEEDED` 与 `MEAL_RECOMMENDATION` 在当前编排中都会进入槽位检查。因此多轮任务的部分轮次允许这两种入口，但仍严格检查是否应追问，以及是否最终完成任务。

## 执行

环境：Java、Maven、Python 3、可连接的 MySQL，真实模型模式还需要本机 `DASHSCOPE_API_KEY`。

在项目根目录（包含 `pom.xml` 的目录）执行：

```powershell
# 不调用模型、不访问数据库：评测逻辑与回归单测
python -m unittest discover -s eval -p 'test_*.py'
mvn test

# 真实模型小样本，6条意图 + 3组任务
.\eval\run.ps1 -Mode smoke

# 真实模型完整集，600条意图 + 100组任务；会使用已配置模型的API额度
.\eval\run.ps1 -Mode live -Workers 3

# 外部Agent响应受控，HTTP、Java服务、MySQL、Trace落库真实运行
.\eval\run.ps1 -Mode fault

# 对已保存的记录重新汇总，不再调用模型
python eval/metrics.py eval/runs/<run-directory>

# 标注版本收紧后，对同样的已保存响应重新评分；输出到新目录，保留原报告
python eval/regrade.py eval/runs/<completed-source> eval/runs/<new-regraded-run>
python eval/metrics.py eval/runs/<new-regraded-run>
```

脚本优先使用当前进程环境中的密钥；为空时读取当前 Windows 用户、机器环境变量，不打印密钥。模型名和服务地址沿用项目配置。

每次评测创建随机命名的 `diet_eval_<12位随机字符>` 数据库，并仅在新建库中执行仓库 SQL。**不会对原 `diet_db` 初始化、清表或写入测试会话。** 新库保留原始证据，评测结束后不自动删除。

基线使用仓库 SQL 数据快照，只有 **4 道公共餐食**。没有为了提高成功率补充餐食，也没有访问或复制用户原数据库里的私人餐食。数据库覆盖不足会真实反映在零结果和任务失败中。更换餐食库是另一个实验条件，需要重新报告数据版本。

## 指标

| 指标 | 分母与成功条件 |
|---|---|
| 意图路由准确率 | 全部计划执行的意图样本；最终路由等于标注 |
| 端到端任务成功率 | 全部计划执行的多轮任务；所有轮次的响应类型、路由、槽位、非空推荐、历史排除和多餐覆盖要求均满足 |
| 槽位补全成功率 | 60组补槽任务；最终累计槽位包含必要值，并且不超出已标注的允许值 |
| 重复率 | 调整轮展示的餐食总数；分子为历史已展示过的餐食条数。没有任何展示时报告未测，不报0% |
| 换新成功率 | 所有调整轮；非空、无历史重复且该轮其他验收条件全部满足 |
| 白名单合规率 | 有卡片的响应；所有卡片ID属于本轮实际允许候选。普通推荐仅允许重排Top3，多餐规划使用实际选中餐食 |
| Trace覆盖率 | 预定义场景关键节点实例；存在可解析的结构化记录，Agent调用另检查耗时和输出/异常 |
| 降级可用率 | 120次故障注入；目标Agent确实被调用，5秒内返回场景对应的有效结构和非空文本 |

零分母显示“未测/不适用”。缺失的意图或任务结果保留在分母，部分执行报告不能当作完成整个测试集。空卡片不计入白名单成功；要同时看任务成功率和空推荐次数。

Trace覆盖不代表所有HTTP入口覆盖、Java行覆盖或Token完整率。HTTP参数校验和加载会话在当前业务Trace之前；模型没有提供usage时Token保持缺失。

## 故障注入范围

三种故障、四个Agent、每组重复10次，共120次：

- 意图、推荐回复、多餐回复：已抛出的超时异常、空字符串、非法JSON。
- 澄清Agent：已抛出的超时异常、空字符串、空响应对象。**澄清Agent的合法输出是自然语言，不要求JSON，因此不把非法JSON解析算作其故障类型。**

网络边界使用Mockito的`ReActAgent`替身。实际调用链、JSON解析、规则降级、HTTP响应、数据库和Trace仍使用项目代码。此组数据不能计入真实LLM准确率。

`TIMEOUT_EXCEPTION`测的是**底层已经发出超时异常后能否兜底**；不证明无限挂起的网络请求能按时取消。当前业务调用的 `.block()` 未传递显式时限，此限制需单独验证/改造。

## 输出与复核

每个 `eval/runs/<run>` 包含：

- `manifest.json`：本次实际纳入的样本及环境、数据来源信息。
- `observations.jsonl`：逐样本输入、实际输出、保存的Trace、是否成功、失败原因。
- `metrics.json`：分子、分母、比例、各类意图准确率与混淆矩阵。
- `report.md`：可读报告。
- `completed.txt`：真实模型模式全部任务执行完毕的标记；运行失败时不生成。

`HistoryExclusionTest`额外验证30组候选充足的Java规则场景，每组连续换3批，观察270条推荐。结果保存在`target/history-exclusion-metrics.json`。它验证重排过滤与历史累计，不计入真实模型100组任务的重复率或成功率。

优先复核否定/引用表达、健康风险、补槽失败与所有异常记录。标注有误时先记录修改原因、递增数据版本，再统一重跑；不要只删除失败样本。

## 本次必要修复

`AgentTraceService` 使用独立复制的Jackson映射器，按字段序列化Lombok fluent DTO。原实现会在序列化失败后保存`SessionState(...)`、`MealItem(...)`等字符串，无法可靠重建候选集合。`TracePayloadTest` 在原实现下失败，修复后通过；没有改变路由规则、Prompt、推荐排序或原HTTP序列化配置。
